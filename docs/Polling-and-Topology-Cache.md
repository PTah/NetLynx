# Опросы и кэш топологии (blast-graph)

**Перевод:** [English version](en/Polling-and-Topology-Cache.md)

Как NetLynx **собирает** данные о сети и **запоминает** граф связности.

Коротко: **ночного** обхода всей сети (автоматический ping-sweep / скан неизвестных подсетей по расписанию) **нет**. Сеть узнаётся **постоянно** через SNMP-поллер уже известных узлов в inventory. Отдельно: **ручной** скан management-подсети по SNMP — Настройки → Инвентарь → «Сканирование сети» (см. [Autodiscover.md](Autodiscover.md)). Ночью пересобирается **кэш графа** для blast/путей из уже накопленных LLDP/CDP/manual рёбер.

См. также: [Autodiscover.md](Autodiscover.md) (SNMP+LLDP на свитчах), [Config-History.md](Config-History.md) (снимки конфигов).

## Слои

### 1. Живой сбор (днём и ночью одинаково)

Планировщик поллера (`POLL_SCHEDULER_SECONDS`, у каждого узла свой `poll_interval_seconds`) опрашивает устройства из списка **Узлы**:

| Что читает | Куда пишет / зачем |
|------------|--------------------|
| LLDP / CDP соседи | `port_neighbors` → кандидаты «Обнаружено»; рёбра карты топологии |
| FDB / MAC | живой снимок FDB, события, линки FDB→топология |
| IF-MIB, PoE, CPU, Printer-MIB… | карточка узла, метрики, графики |

Новые устройства **сами не попадают в Узлы** — только в «Обнаружено». В inventory их добавляют вручную (promote с порта / топологии / списка обнаруженных).

Код: `internal/poller`, запись соседей — `UpsertPortNeighbors` / `SyncDiscoveredFromNeighbors`.

#### Как поллер решает, что узел «пропал»

| Правило | Поведение |
|---|---|
| «В сети» | `auto`: ICMP **или** SNMP; `ping`: только ICMP (SNMP не опрашивается); `online`/`offline` — ручная отметка |
| `DEVICE_OFFLINE` (обычно) | после **2 подряд** неудачных опросов — короткий SNMP-блип при живом ICMP письма не даёт |
| `DEVICE_OFFLINE` (пропажа) | **сразу на первом опросе**, если узел, который раньше отвечал на ICMP, замолчал и по ICMP, и по SNMP (это уже не блип) |
| `DEVICE_ONLINE` | при первом успешном опросе после зафиксированного эпизода оффлайна |
| Рестарт NetLynx | счётчик подтверждений in-memory; если процесс перезапустили посреди простоя, `DEVICE_OFFLINE` догоняется, когда простой превышает 2 интервала опроса (не менее 3 минут) |

#### Лёгкий и тяжёлый опрос

Опрос разделён на два уровня, чтобы падение критичных узлов видеть сразу, а большие таблицы не гонять каждую минуту.

| Уровень | Что делает | Периодичность |
|---|---|---|
| **Лёгкий** | ICMP-ping, `sysDescr`/`sysUpTime`, IF-MIB (статусы портов, счётчики, скорость), LINK_UP/LINK_DOWN, flap, утилизация, CPU, ИБП-UPS-MIB, тонер МФУ | `poll_interval_seconds` узла (для критичных — не реже `POLL_CRITICAL_INTERVAL_SECONDS`, по умолчанию 15 с) |
| **Тяжёлый** | LLDP/CDP-соседи, ARP, PoE (PSE-MIB + SSH-фолбэк + LLDP-PD), STP, chassis MAC, роли портов, FDB (`FDB_POLL_INTERVAL_SECONDS`) | `devices.heavy_poll_interval_seconds` (в карточке узла «Тяжёлый опрос (с)»; пусто/`NULL` = `POLL_HEAVY_SECONDS`, по умолчанию 300 с) |

Приоритет типов узлов (влияет на очередность и на верхнюю границу лёгкого опроса):

| Приоритет | Типы | Интервал |
|---|---|---|
| Критичный | роутер, коммутатор, сервер | не реже 15 с (`POLL_CRITICAL_INTERVAL_SECONDS`) |
| Важный | ИБП, NAS, компьютер, iLO/IPMI | интервал из карточки |
| Обычный | SIP-телефоны, камеры, МФУ, ТВ и т.д. | интервал из карточки |

На лёгком опросе поля, которые приходят только с тяжёлым (PoE-флаги, роли портов), **не перезаписываются** — `UpsertInterfaces` сохраняет прежние значения (`COALESCE` / роль из снимка).

История util/rate пишется не чаще `METRICS_UTIL_INTERVAL_SECONDS` (по умолчанию 60 с): лёгкий опрос может идти каждые 15 с, но столько строк графику не нужно — без троттлинга `metric_samples` растёт до ~19 млн строк/сутки вместо ~10 млн (≈1 семпл на порт в минуту).

Очередь опроса: планировщик (`POLL_SCHEDULER_SECONDS`, по умолчанию 10 с) берёт все просроченные узлы, **сортирует по величине просрочки** (`overdueBy`) и опрашивает до 40 параллельно. Узел, у которого молчит ICMP, проверяется SNMP с коротким таймаутом (2 с без повторов) — мёртвое устройство не растягивает цикл на 10+ секунд, иначе ребут в этом «слепом окне» остаётся незамеченным.

#### Узлы без SNMP-агента (backoff)

Для устройств, которые отвечают на ICMP, но не отвечают по SNMP (камеры, ПК, ТВ, часть АР), после **3 сбоев подряд** SNMP-опрос приостанавливается на **15 минут** — ICMP при этом продолжает работать, достижимость и `DEVICE_OFFLINE`/`DEVICE_ONLINE` считаются как обычно. Успешный SNMP-опрос сбрасывает счётчик. Это экономит слоты опроса: без backoff такие узлы давали ~70 таймаутов в минуту по 5–10 секунд каждый.

Если у узла есть SNMP, но временно пропал (перезагрузка агента), backoff сам снимет паузу через 15 минут и опрос возобновится.

#### FDB на узлах без bridge-MIB

Если опрос FDB не удался («bridge port map empty» — серверы, часть АР, узлы без `BRIDGE-MIB`), попытка всё равно отмечается в `last_fdb_poll_at`: такой узел не пробуется на каждом тяжёлом опросе, а ждёт свой `FDB_POLL_INTERVAL_SECONDS`. Статус на карточке — «FDB недоступен».


### 2. Ночной (и периодический) пересчёт blast-кэша

Это **не** новый SNMP-обход сети. Job берёт уже известные рёбра из БД и пересобирает сжатый граф для анализа влияния (VLAN delete, shut-impact, L2-path, loops, path A→B).

Реализация: `internal/topologycache` (`Hub.Run`, `Rebuild`).

Триггеры:

| Триггер | Когда |
|---------|--------|
| `startup` | старт `netlynxd` |
| `hourly` | раз в `TOPOLOGY_BLAST_CACHE_INTERVAL_MINUTES` (по умолчанию 60 мин) |
| `night` | wall-clock час `TOPOLOGY_BLAST_NIGHT_HOUR` (по умолчанию **3:00**), один раз в сутки |
| `event:…` | после poller / ручных линков, debounce ~45 с (`NotifyDirty`) |

Шаги `Rebuild`:

1. `BuildTopologyGraphFiltered` — узлы inventory + рёбра из `port_neighbors` / manual (без stale).
2. Выбор root (STP preferred / эвристика).
3. BFS-дистанции, VLAN на рёбрах.
4. Атомарная запись кэша + строка истории.

Таблицы: `topology_blast_meta`, `topology_blast_edges`, `topology_blast_dist`, `topology_blast_edge_vlans`, `topology_blast_history` (хранение ~`TOPOLOGY_BLAST_HISTORY_DAYS`, по умолчанию 30).

Карта в UI («Топология») строится из живых `port_neighbors` и связанных данных; blast-кэш — скелет для расчётов «что отрежется / куда пойдёт путь».

### 3. Другие фоновые задачи «раз в сутки»

| Задача | Расписание | Что помнит |
|--------|------------|------------|
| **FDB daily snapshots** | после успешного FDB-poll, не чаще ~20–24 ч (`FDB_SNAPSHOT_*`) | история «где MAC был N дней назад» |
| **Config snapshots** | интервал ~24 ч (`CONFIG_SNAPSHOT_*`) | `show run` / diff на карточке узла |
| **SSH backup** | wall-clock из UI (час/минута в настройках бэкапа) | архивы конфигов свитчей |

FDB и config — **интервальные**, не привязаны к 3:00. Backup ближе к «ночному», но это бэкап конфигов, не топология.

## Схема потока

```text
SNMP poll (постоянно, inventory)
  → port_neighbors / FDB / metrics / discovered
  → (debounce) NotifyDirty
       ↘
TopologyCache Hub: startup | hourly | night@03:00 | event
  → Rebuild из БД (без SNMP)
  → topology_blast_* + history
```

## Переменные окружения

См. `.env.example`:

| Переменная | Смысл | По умолчанию |
|------------|--------|--------------|
| `TOPOLOGY_BLAST_CACHE_ENABLED` | вкл/выкл кэш | `true` |
| `TOPOLOGY_BLAST_CACHE_INTERVAL_MINUTES` | периодический rebuild | `60` |
| `TOPOLOGY_BLAST_NIGHT_HOUR` | час ночного rebuild (0–23) | `3` |
| `TOPOLOGY_BLAST_HISTORY_DAYS` | срок истории снимков кэша | `30` |
| `FDB_SNAPSHOT_ENABLED` / `_INTERVAL_HOURS` / `_RETENTION_DAYS` | дневные снимки FDB | см. `.env.example` |
| `CONFIG_SNAPSHOT_ENABLED` / `_INTERVAL_HOURS` / `_RETENTION_DAYS` | снимки конфигов | см. `.env.example` |

## Итог

- **Устройства / соседи / MAC** — непрерывный SNMP-poll + БД.
- **«Ночной обход» в коде** — пересборка кэша связности в `TOPOLOGY_BLAST_NIGHT_HOUR` (+ hourly и по событиям), **без** повторного сканирования LAN.
- **Полный ночной discovery неизвестных IP** не реализован.
