# Техническое задание: система мониторинга коммутаторов по SNMP

Исходное описание продукта (черновик). **Актуальная сверка с кодом** — в [§12](#12-статус-реализации-актуально-на-05x); план работ — [Roadmap.md](Roadmap.md), [To-Do.md](To-Do.md).

Аналог принципов Zabbix, фокус на L2/L3-коммутаторах. Интерфейс — **веб**; отдельный Windows desktop-клиент в ТЗ закладывался, но **не готов** ([desktop/README.md](../desktop/README.md)).

## 1. Цель и границы

**Цель:** серверное приложение с веб-интерфейсом, которое по списку коммутаторов пользователя циклически опрашивает их по **SNMP**, хранит состояние и историю, формирует **события** (триггеры / проблемы / восстановления) и показывает их на дашборде. Отдельно важно отслеживать **link down** и **link up**.

**MVP (изначально):** мониторинг коммутаторов — порты, доступность, базовые метрики, веб, API под будущий клиент.

**Было «вне scope на старте», но уже реализовано (см. §12):** LLDP/CDP/FDB-топология и карта, discovered → promote, RBAC, email/Telegram/webhook, бэкапы, управление портами, вендоры W1/W2, расследование MAC / петли / postmortem, config snapshots.

**По-прежнему вне scope или не сделано:** NetFlow/sFlow, полноценный Windows desktop-клиент, TimescaleDB, remote pollers / федерация нескольких серверов.

## 2. Термины

- **Узел (коммутатор):** IP/DNS, SNMP v2c/v3, community / учётные данные, профиль вендора (опционально).
- **Опрос (poll):** периодический SNMP GET / GETBULK по набору OID.
- **Событие:** зафиксированное изменение состояния или пороговая ситуация (линк вниз/вверх, недоступен SNMP, высокая загрузка CPU и т.д.).
- **Проблема / OK:** как в Zabbix — «есть проблема» / «проблема снята».

## 3. Функциональные требования

### 3.1. Управление коммутаторами

- Добавление / редактирование / удаление коммутатора.
- Поля минимум: имя, адрес, **SNMP v2c и/или v3** (на каждый узел — выбранная версия и свои параметры: community для v2c; user, authPriv и т.д. для v3), **интервал опроса** (глобальный дефолт + переопределение на узле), таймаут / ретраи.
- Проверка SNMP вручную (кнопка «Test») с отображением sysName/sysDescr.
- Статус узла: **онлайн/оффлайн** (SNMP отвечает / не отвечает), время последнего успешного опроса, RTT (опционально).

### 3.2. Мониторинг портов (ключевая часть)

- Обнаружение интерфейсов через `IF-MIB` (`ifDescr`, `ifType`, `ifAdminStatus`, `ifOperStatus`, `ifSpeed` / `ifHighSpeed`).
- Исключения: фильтр «не мониторить» (например, VLAN SVI, loopback, aggregate — по типу / имени / шаблону).
- **События по линку:**
  - **Link DOWN:** `ifOperStatus` перешёл в `down` (или эквивалент) при `ifAdminStatus = up` (чтобы отличать административно выключенный порт).
  - **Link UP:** `ifOperStatus` стал `up` с предыдущего «не up» — трактуется как **«на порту появился линк»** (подключили кабель / устройство).
- **Нагрузка на порту (обязательное требование):** отслеживать **утилизацию** относительно **номинальной скорости порта** (из `ifSpeed` / `ifHighSpeed` при `ifOperStatus = up`). Расчёт — по счётчикам **IF-MIB** `ifHCInOctets` / `ifHCOutOctets` (предпочтительно 64-bit; при отсутствии — деградация на 32-bit с осторожностью к обёртке счётчика): за два последовательных опроса вычислить **бит/с** по приросту октетов и **времени между опросами**; утилизация **входа** и **выхода** отдельно, для порога брать **максимум из двух** (или настраиваемо «хуже из in/out»). **Порог по умолчанию: 90%** от скорости линка; значение **настраиваемо** глобально и при необходимости на уровне узла/порта. При превышении порога — **событие / оповещение** (тип вроде `PORT_UTILIZATION_HIGH`); при возврате ниже порога с **гистерезисом** (например, событие «OK» только ниже **85%**, настраиваемо) — `PORT_UTILIZATION_OK`, чтобы не дребезжать на границе. На портах без валидной скорости (unknown / aggregate / особые типы) — не считать или явно помечать «N/A». Учесть **сброс счётчиков** и **wrap** при расчёте.
- **Дополнительно (целевое требование, не «nice to have»):** **постараться реализовать отслеживание MAC-адресов на порту** по данным **FDB** (Forwarding Database) из SNMP. Цель — фиксировать появление **ранее не виданного** MAC на **access-порту** (эвристика «подключили чужое устройство / возможный интруз»), а также исчезновение известного MAC и смену привязки MAC↔порт. Учесть ограничения: размер FDB, таймауты записей, агрегаты / MLAG, один MAC на нескольких портах при изучении, различия **BRIDGE-MIB** / **Q-BRIDGE-MIB** (`dot1dTpFdbEntry`, `dot1qTpFdbEntry`) и сопоставление **bridge port → ifIndex** (`dot1dBasePortIfIndex`). Если на конкретном вендоре полный опрос FDB нереалистичен по времени — предусмотреть **редкий интервал** опроса FDB отдельно от быстрого опроса `ifOperStatus`, батчи **GETBULK**, и деградацию до только Link UP/DOWN с явным статусом «MAC-мониторинг недоступен» для узла.

### 3.3. CPU и базовые метрики

- **CPU:** через вендор-специфичные OID или стандартные там, где есть (часто нужен **профиль вендора**: Cisco, Juniper, MikroTik и т.д.; универсального «одного OID для всех» нет).
- Заложить **плагинную модель профилей:** «набор OID + правило парсинга».
- Опционально позже: память, температура.

### 3.4. Оповещения и события

- Журнал событий с типом, серьёзностью, узлом, порту (если применимо), временем, «до / после».
- В том числе события по **перегрузке порта** (см. п. 3.2): превышение порога утилизации и восстановление ниже порога с гистерезисом; в payload события — **фактическая утилизация in/out (%)**, порог, скорость порта, интервал усреднения (если есть).
- **Реакция на инциденты (MAC / интруз и аналоги):** на **первом этапе** — **только оповещения** (события в UI, журнал, внешние каналы по мере готовности). **На будущее** заложить возможность **авто-блокировки порта** (например, административное выключение порта через расширяемый механизм действий — SNMP SET / вендорный API / сценарий вне продукта — конкретика на этапе проектирования модуля «действия»): функция **по умолчанию выключена**, включается и настраивается явно в **настройках** (per-site или per-device), с аудитом и правами доступа.
- Правила уведомлений (позже): email / Telegram; в MVP — только UI + webhook опционально.

### 3.5. Веб-интерфейс (макет)

- **Слева:** навигация в стиле Zabbix: **Дашборд**, **Узлы (коммутаторы)**, **События**, **Настройки** (SNMP-профили, пользователи, системные параметры).
- **По центру (Дашборд):**
  - **Верх:** таблица / карточки коммутаторов: имя, онлайн/оффлайн, **CPU %** (или N/A), время последнего опроса.
  - **Ниже:** лента **событий** (последние N, фильтр по узлу / типу / времени).
- Отдельные экраны: детализация по коммутатору (порты, текущее состояние, **текущая утилизация in/out**), история метрик (графики).

### 3.6. Клиент-сервер и будущий Windows-клиент

- Сервер предоставляет **HTTP API** (REST + при необходимости WebSocket для live-обновлений дашборда).
- Веб — отдельный фронтенд или SSR; контракт API должен быть стабильным для будущего Win-клиента.

## 4. Нефункциональные требования

- **Начальный этап / MVP:** не более **100 коммутаторов** в одной инсталляции (см. п. 11). Архитектура поллера и БД — с **запасом на рост** (без обязательства поддерживать тысячи узлов в первой версии).
- Ориентир нагрузки: порядок **10⁴–10⁵** интерфейсов при масштабировании (асинхронный опрос, батчи); для 100 коммутаторов типичный объём — комфортный режим по умолчанию.
- Надёжность: поллер не должен блокировать весь сервер при таймаутах (лимиты воркеров / очередей).
- Аудит: кто менял настройки (когда появится multi-user).
- Логи поллера отдельно от API.

## 5. Архитектура (логическая)

```text
[Browser] ──HTTPS──> [API + Web static]
                         │
                    [PostgreSQL / TimescaleDB]
                         ▲
                         │
              [Poller Service] ──SNMP──> [Коммутаторы]
                    │
              (очередь задач / планировщик)
```

**Компоненты:**

1. **API-сервис:** CRUD узлов, настройки, выдача событий / статусов, аутентификация.
2. **Poller (воркеры):** планировщик интервалов, SNMP-запросы, нормализация данных, детектор изменений → запись событий и текущего состояния.
3. **БД:** реляционная для конфигурации и событий; для метрик — либо тот же Postgres с **TimescaleDB**, либо отдельное TS-хранилище позже.

**На рост:** вынести поллер в отдельный процесс / контейнер, масштабирование по узлам.

**Модель развёртывания (как у Zabbix на одном сайте):** одна **логическая инсталляция** на организацию/площадку — **один сервер** (API + веб + поллер + БД на одной ВМ или разнесённые процессы на одном сайте). **Распределённых remote pollers**, федерации нескольких серверов и «облака регионов» **в первой версии нет**; при необходимости другой площадки — вторая независимая инсталляция продукта.

### 5.1. Платформа сервера: Linux и Windows Server

**Да, серверную часть можно разворачивать на Windows Server** — это не противоречит ТЗ: SNMP-опрос, HTTP API и веб-интерфейс не привязаны к ОС, если стек выбран совместимый.

| Аспект | Linux (типовой вариант) | Windows Server |
|--------|-------------------------|------------------|
| Поллер + API | Бинарник **Go** как служба **systemd** или контейнер; **Python** под **Windows Service** / NSSM | Те же **Go** / **Python** как **Windows Service**; либо **.NET** (Kestrel) для «всё в одной экосистеме Microsoft» |
| СУБД | **PostgreSQL + TimescaleDB** — зрелый путь в документации | PostgreSQL официально поддерживается под Windows; Timescale — проверить версию и поддержку под вашу редакцию Windows **или** метрики в SQL Server / отдельное TS-хранилище (усложняет единую схему) |
| Веб | Статика за nginx / встроено в процесс API | IIS как reverse proxy к Kestrel / Go, или только внутренний порт + внешний балансировщик |
| Эксплуатация | Чаще привычны контейнеры и Ansible | Удобно, если в организации уже лицензии, AD, мониторинг MS, политика «всё на Windows» |

**Вывод для ТЗ:** целевой эталон развёртывания описывать для **Linux + PostgreSQL** (проще воспроизводимость и CI). **Windows Server** зафиксировать как **поддерживаемый вариант**: те же сервисы в виде Windows Service, те же порты и API; отличия вынести в документ «Установка под Windows» (пути, служба, firewall, учётная запись службы, резервное копирование БД).

## 6. SNMP: опрос в MVP

| Задача           | MIB / OID (идея) |
|------------------|------------------|
| Идентификация    | SNMPv2-MIB `sysObjectID`, `sysName`, `sysDescr` |
| Интерфейсы/линк  | IF-MIB `ifTable` / `ifXTable` |
| Утилизация порта | IF-MIB `ifHCInOctets`, `ifHCOutOctets` (или `ifInOctets` / `ifOutOctets`), скорость из `ifHighSpeed` / `ifSpeed` |
| CPU              | Профиль вендора |
| «Новый клиент»   | MVP: **Link UP**; затем **FDB / MAC по портам** (см. п. 3.2); опционально LLDP / CDP |

## 7. Выбор языка (рекомендация)

| Вариант   | Плюсы | Минусы |
|-----------|--------|--------|
| **Go**    | Конкуррентность, один бинарник, деплой, SNMP-библиотеки | UI отдельно |
| **Rust**  | Производительность / безопасность | Дольше разработка |
| **Python**| Быстрый старт, pysnmp | Под большой нагрузкой сложнее удерживать производительность |
| **Java**  | Зрелая экосистема | Тяжелее для «маленького» продукта |

**Практичная рекомендация:** **Go** для **сервера + poller + API**, **TypeScript (React / Vue / Svelte)** для веб-морды. Альтернатива для прототипа: Python (FastAPI) + React с пониманием узкого места poller при росте.

**Если приоритет — размещение только на Windows Server и стек Microsoft:** **C# / .NET** (worker Windows Service для SNMP + ASP.NET Core для API + Blazor или SPA на TS) остаётся рабочим выбором; SNMP-библиотеки и модель «поллер отдельно от UI» сохраняются.

## 11. Принятые решения (ранее открытые вопросы)

1. **Реакция на инциденты (в т.ч. MAC / интруз):** на первом этапе — **только оповещения**. В архитектуре и настройках **предусмотреть на будущее** опциональную **авто-блокировку порта** (по умолчанию **выключена**, включается явно в настройках). Детали механизма (SNMP write, вендорные API и т.д.) — на этапе проектирования модуля «действия»; см. также п. 3.4.
2. **Масштаб:** под «ориентиром» имелось в виду **ожидаемое число коммутаторов** в одной инсталляции. Зафиксировано: на **начальном этапе** — **не более 100 коммутаторов** (см. п. 4). Конкретные **интервалы опроса** IF-MIB и FDB остаются настройками продукта с разумными дефолтами (вынести в конфиг при реализации).
3. **SNMP:** требуется поддержка **и v2c, и v3**; на каждом узле задаётся используемая версия и параметры.
4. **Топология развёртывания:** **один сайт** — одна инсталляция в модели «как Zabbix» (см. п. 5); без remote pollers в первой версии.
